# Scripts

All scripts are standalone (no install step). Each has a `--help` and a
top-of-file docstring.

## Typical invocation order in a batch

```
# 1. Always start with a fresh pull (no cookies needed for the all-fields path)
python gem_query.py --all-fields lng -o gem_export.csv   # gem_all_fields.py is the library; running it directly is a no-op
python pull_gem_db.py --map-only --out gem_export.csv   # derive the .colmap.json

# 2. Build the matching indexes
python dedup_index.py

# 3. Run any triage/discovery/update/reconciliation-specific scripts:
python stale_sweep.py                                       # triage/update: dormancy flags + dev_pipeline worklist
python completeness_sweep.py                                # update (standard tier): blank-ref fill targets
python giignl_extract.py ../data/GIIGNL-2026-Annual-Report-0526b.pdf \
    --output ../batches/staging/recon/giignl2026/giignl_extracted.csv --year 2026   # recon phase 1 (archive: data/, see data/README.md)
python report_diff.py --report giignl --extracted ../batches/staging/recon/giignl2026/giignl_extracted.csv \
    --gem-csv gem_export.csv --output ../batches/staging/recon/giignl2026/giignl_diff.json   # recon phase 2
python fsru_sync_check.py                                    # if batch touches FSRUs

# 3b. QC pass (backward-looking; produces a memo, no xlsx — see docs/sops/qc.md)
python completeness_sweep.py                                 # mechanical: blank/orphan refs, missing fields
python stale_sweep.py                                        # mechanical: dormancy + dev_pipeline counts
python dedup_index.py                                        # mechanical: project-key collisions (dup terminals)
python citation_qc.py --country "<C>"                        # link-rot on existing [ref] URLs
python apply_check.py --batch ../batches/<applied>.xlsx      # did the last applied batch land?

# 4. Build the xlsx (staged inputs from batches/staging/ — recon/<edition>/, <scope-slug>/, or <region>/_build)
python build_review_package.py --mode update --inputs-dir ../batches/staging/<scope-slug> \
    --output ../batches/lng_terminals_batch_<stamp>_ET_<scope>_<mode>.xlsx

# 5. Verify no formula errors
python recalc.py ../batches/...
```

## Script-by-script

### Data acquisition

| Script | Purpose |
|---|---|
| `gem_query.py` | Queries the GEM read-only Postgres database directly and exports to CSV. Lowest-level acquisition tool. |
| `gem_all_fields.py` | Reproduces the website's "all-fields" LNG terminal CSV. **No cookies needed** — preferred fresh-pull path. |
| `gem_export_via_web.py` | Downloads the all-fields CSV from the running GEM website. Cookie-based (auth from `.env`). |
| `pull_gem_db.py` | Wraps a data-pull and derives the 115-column index map, writing `.colmap.json` next to the CSV. Use `--map-only` to derive the colmap from an existing CSV without re-pulling. |
| `fetch_timeline.py` | Pulls the full status timeline for a single UnitID from the live DB web UI. Required before any status timeline edit — the CSV export doesn't include timeline data. **Parser is heuristic — verify against the live UI for at least one unit per batch.** **Known issue: the default Heroku host is stale (404) — set `GEM_PROJECT_DB_BASE_URL`; until reachable, route status changes to qa notes, don't stage a blind timeline edit.** |
| `giignl_extract.py` | Parses the GIIGNL annual-report PDF into a flat CSV with GEM-aligned columns. Uses `pdftotext -layout` + column-position row partitioning; per-country capacity subtotals act as block-boundary budgets. Every edition 2020–2026 is committed in `data/` (all real PDFs v1.4–v1.7; see `data/README.md`); offsets are 2026-tuned, so older editions need re-derivation. (The legacy zip-of-JPEGs + OCR vision pipeline lives in git history if a future download reverts.) |

### Normalization and validation

| Script | Purpose |
|---|---|
| `normalize.py` | Canonical names for countries, entities (owners/operators), capacity units, and terminal names. Also transliterates non-Latin names (e.g. Chinese `LocalNames`) to English via jieba + pypinyin for cross-script alias matching. Also exposes `effective_status(status, substatus)` — the planned/actual rule (an `operating`/`construction` unit with substatus `planned` is effectively `proposed`; see `docs/reference/lifecycle_rules.md`). Import as a library; CLI runs smoke tests. |
| `capacity_normalize.py` | mtpa/bcm/y conversion, range parsing (records max per methodology). |
| `status_timeline.py` | Validates legal state transitions, anchor year invariants, current-status derivation. Used by build_review_package.py. |
| `add_effective_status.py` | Appends an `EffectiveStatus` (+ `StatusRuleApplied`) column to a handoff/archive export via `normalize.effective_status`, leaving the raw 115-column schema intact. `report_diff.py` already applies the rule internally, so the working `gem_export.csv` doesn't need it — this is for snapshots handed to the user (e.g. the timestamped `data/gem_export_<stamp>_ET.csv`). **Snapshot retention:** when `-o` is a timestamped `gem_export_<YYYYMMDD>_<HHMM>_ET.csv` archive snapshot, it keeps only the `--keep` most recent such snapshots in that directory and prunes older ones (**default 2**) — so the local CSV archive never piles up. Self-scoping: only fires when the output is itself an archive snapshot, and only ever deletes siblings matching that same name pattern (the working `gem_export.csv` and any other name are untouched). `--keep -1` disables pruning. |

### Search and dedup

| Script | Purpose |
|---|---|
| `dedup_index.py` | Builds project/sponsor-country/unit indexes from the GEM CSV. Bare `python dedup_index.py` writes the indexes; `python dedup_index.py match <candidates.json>` scores discovery candidates against GEM and implements the Discovery SOP §6 similarity comparison (steps 4-6) — name ratio (incl. `OtherNames`), haversine location distance, capacity ratio, and the cancelled/shelved + new-proposal "dead-and-revived" case — emitting a per-candidate `verdict` + `recommended_route` (`discovery_new` / `update_existing` / `update_dead_and_revived` / `manual_review`) to `work/dedup_matches.json`. Library: `match_candidate(cand, build_indexes(csv))`. |
| `monitor_store.py` | Maintains the durable cross-batch monitor list (`monitor_list/current.json`) — the Discovery SOP §5 roll-forward loop. `seed <inputs-dir>` copies the durable store → `<inputs-dir>/prior_monitor_list.json` (run **before** a `--mode discovery` build so the sheet's roll-forward starts from accumulated state); `update <inputs-dir> [--batch <label>]` folds the batch's `staged_monitor_list.json` back into the durable store and **drops candidates promoted to `new_terminals`** (run **after** the build). `show` prints the store. |
| `entity_lookup.py` | Searches local CSV (and optionally remote entity system) for an entity name. Run before staging any new entity. |
| `url_verifier.py` | HTTP 200 + content check + soft-error detection. Every cited URL must pass before being staged. |
| `imo_tracker.py` | Look up FSRU/FLNG vessel IMO via marinetraffic.org. |

### Workflow-specific

| Script | Purpose |
|---|---|
| `stale_sweep.py` | Flags units exceeding lifecycle dormancy thresholds, AND always emits the `dev_pipeline` block — every proposed/construction/shelved unit, annotated `recently_updated` (`--pipeline-recent-months`, default 3) — which is the standard-tier Update worklist (Update SOP §2.1). Used by triage, QC, and update batches. |
| `sweep_worklist_split.py` | Regional-sweep dispatch helper (Update SOP §2.1): merges the standard-tier worklist (`stale_sweep` flagged_units ∪ dev_pipeline ∪ `completeness_sweep` blank-ref gaps), restricts to `Fuel == LNG`, and splits it per country using `batches/staging/_region_map.json`. Writes one `work/sweep/<region>/<slug>.worklist.json` per country with a non-empty worklist plus `work/sweep/_index.json` (counts for dispatch planning — zero-worklist countries get no update agent; `by_state` breakdown for countries over `--shard-state-threshold`, default 40). Run after the fresh pull + `stale_sweep.py` + `completeness_sweep.py`. |
| `citation_qc.py` | QC link-rot sweep (QC SOP §3.2): batch re-verifies existing `[ref]`-column URLs from the export via `url_verifier.py`'s library mode. Verdicts: `dead` (hard rot — counts toward the >25% per-country escalation) / `blocked` (bot-wall/paywall, verify manually) / advisory `name_found`. Scope `--country`/`--status`, cap `--max-urls` (truncation recorded, never silent), politeness `--delay` (url_verifier itself never sleeps). Writes `work/citation_qc.json`. |
| `apply_check.py` | QC post-apply check (QC SOP §3.4): reads an applied batch xlsx's `updates` sheet **by header name** and compares each staged edit against a fresh export — `applied` / `not_applied` / `diverged` (transcription-error catcher) / `not_found` / `reverify_only`. Equal-float values auto-normalize ("8" vs "8.0"); other format-only divergences are reviewer judgment. Writes `work/apply_check.json`. |
| `report_diff.py` | Reconciliation diff between an industry report (GIIGNL or IGU) and current GEM data. Parameterized on report type. Three-pass matching (canonical name → alias via `OtherNames`/`LocalNames` + transliterations → fuzzy); project key includes `section_type` so a mixed liquefaction+regasification terminal splits into two projects rather than summing. Report rows ending in "Expansion"/"Extension" fold into their base `<Site>` row (when a base partner resolves) so phased terminals sum correctly; the `report_sites_merged` field records each fold. Set iterations are sorted, so the diff is reproducible run-to-run. Also auto-discovers `giignl_fsru_fleet.json` beside the extracted CSV (or `--fsru-fleet`): a gem_only FSRU matched (by vessel name or site token) to a fleet-table deployment is tagged `report_fleet_match` so the build routes it as `gem_only_in_fsru_fleet` ("GIIGNL lists it in the fleet table") instead of "report doesn't list it" — so run `giignl_fsru_fleet.py` first. |
| `giignl_fsru_fleet.py` | Parses the GIIGNL "FSRU FLEET AT THE END OF \<year\>" table (2026: PDF p.43, 54 deployed + 4 orderbook) → `giignl_fsru_fleet.json`. Fixed-column slicing (Built/Converted, Vessel Name + "(ex …)", Storage m³, CCS, Send-out MTPA, Owner, Builder, Location), with location-wrap merging for vertically-centered "Site, Country" deployments. **Separate from `giignl_extract.py` (clean table, NOT the hardened country-table machinery).** The build matches each vessel to a GEM FSRU terminal (vessel name → location) for the `giignl_fsru_fleet` sheet — this catches FSRUs the country tables omit (Tema LNG / "Torman"). Older editions move the page (p.20/p.11/p.23/p.33/p.29/p.43 for 2020–2025; pass `--page`). |
| `fsru_sync_check.py` | Cross-checks FSRU records between the LNG Terminals project and the LNG Carrier Tracker project. Graceful degradation if carrier backend unavailable. |

## Data-acquisition paths

There are three ways to pull the GEM CSV, in increasing reliance on auth:

- `gem_all_fields.py` — reproduces the website's all-fields export with **no cookies**. Preferred default.
- `gem_query.py` — hits the read-only Postgres DB directly.
- `gem_export_via_web.py` — downloads from the live website using auth cookies from `.env`.

All three are committed to the repo (no longer user-supplied). `pull_gem_db.py`
wraps a pull and derives the column-index map; run it with `--map-only` to derive
the colmap from a CSV you already pulled.

```
normalize.py           ← imported by most others

citation_qc.py         ← reads pull_gem_db output; imports url_verifier
apply_check.py         ← reads an applied batch xlsx + fresh pull_gem_db output
report_diff.py         ← reads pull_gem_db output + giignl_extract output
fsru_sync_check.py     ← reads pull_gem_db output + optional carrier CSV
build_review_package.py ← reads all *.json staged outputs

```

The simplest pattern (`sys.path.insert(0, str(Path(__file__).parent))` at the
top of each script) means scripts can import each other without any install
step. Don't refactor into a package unless you have a specific reason.

## When to read a script's source

Trust the scripts by default — they're versioned scaffolding, not throwaway code. Read the source when behavior surprises you, and specifically when:

| Script | Read source when |
|---|---|
| `gem_all_fields.py` | Export columns/shape change; a pull path fails |
| `pull_gem_db.py` | Schema changed; column indices look wrong; auth fails on the cookie fallback |
| `fetch_timeline.py` | Endpoint moved/unreachable; UI changed; timeline parse returns nothing for a unit known to have one |
| `normalize.py` | Adding new country/entity; cluster matching is over- or under-merging |
| `dedup_index.py` | New batch type that needs a different index shape; the `match` verdict thresholds (`NAME_SIM_*`, `DIST_*_KM`, `CAP_RATIO_NEAR`) mis-route candidates |
| `monitor_store.py` | The durable store carries a stale/duplicate entry; promotion-drop misses a renamed candidate (match is normalized country + name vs `new_terminals`) |
| `capacity_normalize.py` | New capacity unit appears in source; conversion factor disputed |
| `status_timeline.py` | Methodology updates state machine; anomalous transition observed |
| `stale_sweep.py` | Methodology revises the year thresholds (inferred shelved at 2yr, inferred cancelled at 4yr, etc. — `docs/reference/lifecycle_rules.md`); the dev_pipeline status set or recency annotation needs tuning |
| `completeness_sweep.py` | Required-field policy needs tuning; a `[ref]` pair mis-classifies; the coverage reference list needs a country added/fixed (see the `gem_countries_outside_reference` self-check against `country_universe.py`) |
| `citation_qc.py` | Rot rates look implausible; a `[ref]` column isn't being scanned (the column list derives from colmap `*_ref` keys); a bot-walled domain mis-grades as dead (extend the blocked-title hints); delay needs tuning |
| `apply_check.py` | A staged edit reads `diverged` purely from formatting; the `updates` sheet layout changed in `build_review_package.py` (apply_check reads by header name, so renames matter, reorders don't) |
| `entity_lookup.py` | Entity search UI changed; known entity not being found |
| `url_verifier.py` | Verifier flags false positives/negatives; new source pattern needs handling |
| `imo_tracker.py` | marinetraffic.org URL pattern changed; Cloudflare gating |
| `report_diff.py` | Adding a new reconcilable source; match algorithm over/under-merging (full symptom→function map in the deep-dives below) |
| `giignl_fsru_fleet.py` | New edition shifts the column offsets (re-derive from the header) or moves the fleet page; a deployment location fuses with a neighbor; a vessel doesn't match its GEM terminal |
| `fsru_sync_check.py` | Sync conventions change; reassignment detection misfires |
| `build_review_package.py` | Adding a new sheet section (also add a `SHEET_DESCRIPTIONS` entry); changing color convention |
| `recalc.py` | Always run before present_files |

For `giignl_extract.py`, `report_diff.py`, and `build_review_package.py`'s verdict classifier, read the deep-dives below **before editing** — they catalog the edge-case fixes and the symptoms that point at each function.

## Deep-dive: GIIGNL reconciliation internals

The two most intricate scripts in the reconciliation pipeline (`giignl_extract.py` and `report_diff.py`) carry a large catalog of edge-case fixes, each guarding against a specific real-world failure observed in the GIIGNL editions. CLAUDE.md just points here to stay lean; the full rationale lives here. **Read the relevant block below before editing either script** — most of these look like over-engineering until you hit the exact PDF layout they defend against.

### `giignl_extract.py` — GIIGNL PDF parsing

Parses GIIGNL report into a flat CSV with GEM-aligned columns. 2026 edition is a real PDF v1.7 with a clean text layer — uses `pdftotext -layout` + column-position-based row partitioning; per-country capacity subtotals are used as block-boundary budgets so rows route to the right country even when labels appear mid-block. GIIGNL vertically *centers* each country label+subtotal within its block, so rows above the label inherit the previous country; a post-pass (`_truecup_country_subtotals`) reclaims them by *tentatively* pulling rows from the **single immediately-preceding country** and committing only if the run then reaches the country's published subtotal (within a 6%/2% reach band). This catches the case the running budget misses (the previous country's block spilled over from an earlier page so its page-local cumulative never reaches its subtotal — e.g. Brunei T1/T2 inherited Australia, whose 85.8 MTPA block began on the prior page) WITHOUT the failure mode of an earlier naive version: a multi-page country like China regas (264 MTPA, pages 55–57) looks "short" on each page and would otherwise swallow the whole USA+Bangladesh blocks above it to reach its subtotal. The two guards — never pull through more than one preceding country, and commit only on reaching the subtotal — keep it to genuine centered-label misattributions (Brunei, Ain-Sokhna, Damietta, Moheshkhali, Brazilian/Malaysian/German/UK terminals, etc.). The standalone page footer ("<page#> - GIIGNL Annual Report <year> Edition") is skipped during line classification (`_PAGE_FOOTER_RE`) — otherwise the line-merge pass folds it into the last data row of the page and the column slicer splits it across cells (e.g. "Annual" → country "… GIIGNL An" + site "nual Report 2026 Edition"), corrupting that row AND poisoning the country walk for the rest of the page (this had silently dropped QatarEnergy LNG S(2) T4 and mis-countried Ruwais/San Juan/Yamal T1/etc.). **Embedded label/subtotal-on-a-data-row + cross-page blocks (QatarEnergy fix):** GIIGNL also centers a country label+subtotal directly ONTO a data row's physical lines — Qatar's "77.0 MTPA" + "N(3) T6" sit on the N(3) T6 row. A subtotal line is now recorded but NOT skipped when its name column (col 1) carries a fragment, so the trailing train code isn't lost (this had degraded N(3) T6 / S(3) T6 to a bare "QatarEnergy LNG"; the same fix also recovers regas terminal names previously eaten by such lines — Jamaica "Old Harbour", Croatia "Krk expansion", Türkiye "Saros LNG", Ravenna's "BW Singapore" vessel). Because the centered label makes rows ABOVE it inherit the previous country and the per-page `_truecup_country_subtotals` can't repair a block that spans pages (Qatar liq spans 34-35 so neither page reaches 77.0; N(1)/N(2) stranded on Oman, Oman T1 on USA), a section-wide `_reclaim_cross_page` re-runs the reclaim over ALL pages' rows in report order, iterated to a fixpoint (Qatar pulls N(1)/N(2) from Oman → Oman then pulls Oman T1 from USA), choosing the pull count CLOSEST to the subtotal — not merely within band, else Indonesia (24.9) swallows Canada's Tilbury LNG (0.3). It keys off `_robust_subtotal_map` (each subtotal → its NEAREST data row's country, since the sequential walk otherwise mis-files Oman's 11.4 under USA). Zero-width chars are stripped (`_clean_text` + normalize) so "S(2 )" yields designator token "s(2". A regas FSRU row whose EVERY site fragment carries an (FSRU)/(FSU) tag (site "Ravenna (FSRU)" + vessel "BW Singapore (FSRU)") takes the first fragment as site, last as vessel (trailing "and" stripped for dual-FSU rows like Malaysia "Tenaga Empat … and Tenaga Satu"). **Row partitioning by name-start (APLNG/Darwin/Prelude fix):** lines are assigned to the NEAREST data line, NOT split at the midpoint between data lines (the midpoint absorbed a row's leading name into the row ABOVE when a site name spans multiple physical lines). A distance TIE is resolved by content: a capitalized name-START fragment (no capacity, opening/balanced parens, not "Expansion"/"Extension", no FSRU/FLNG tag) is the LEADING name of the row BELOW; a continuation (lowercase, dangling close-paren like "…Ahmeyim Phase 1)", a bare "Expansion", or a facility-tagged vessel like "Italis LNG (FSRU)") stays with the row ABOVE. This un-fuses "APLNG T2" from "Darwin LNG (new" (so APLNG T1+T2 group → 9.0), recovers "Darwin LNG (new supply source Barossa project)", Croatia "Krk" (main row, fixing the earlier fragmentation), "Piombino"/"Panigaglia", and un-merges cross-terminal bleeds (Al Zour+Dakar, Zeebrugge+Krk). A facility tag in PARENTHESES — "(FLNG)"/"(FSRU)" — is NOT stripped as a status hint (it's part of the name: "Prelude (FLNG)", "PFLNG Dua (FLNG)"); `normalize_terminal_name` drops a trailing parenthetical facility tag for MATCHING only ("prelude (flng)"→"prelude" exact-matches GEM "Prelude FLNG Terminal"), keeping the tag in the displayed site_name. **Non-operating status hint → `status` column (Bontang/Balhaf fix):** GIIGNL's liq/regas tables are operating-only, but a few rows are annotated as not-currently-operating with a status parenthetical — "Bontang Train E (Mothballed)", "Balhaf T1/T2 (stopped)", "Atlantic LNG T1 (Mothballed)". `_strip_train_suffix` already peels such a parenthetical off the liq name; `_status_from_hint` now maps the peeled word to a canonical GEM non-op status (`_NONOP_STATUS_HINTS`: mothballed→mothballed, stopped/idle/suspended→idled, retired/decommissioned→retired, …) written to a new LAST CSV column `status` (regas peels its own trailing status paren via `_STATUS_HINT_RE`, since facility-tag stripping leaves a "(Mothballed)" in the site name). An UNRECOGNIZED hint maps to "" (row stays operating, raw hint kept only in notes — we don't guess). report_diff then EXCLUDES a status-bearing row from the operating total. NB: facility tags "(FLNG)/(FSRU)/(FSU)/(FRU)/(FPSO)" are explicitly NOT status hints (kept as part of the name). **Region-tolerant train-suffix strip (`_TRAIN_SUFFIX_RE`, LNG Canada fix):** the train suffix is end-anchored, but GIIGNL tags some Canadian rows with a trailing province — "LNG Canada T1, BC" / "LNG Canada T2, BC". The end-anchor meant the ", BC" defeated the strip: the train code never moved to the `trains` column, the two rows kept distinct names, failed to roll up to one project, and T1 fuzzy-matched GEM at HALF capacity (7-vs-14, bogus 50% conflict) while T2 orphaned into `report_only` ("GIIGNL has, GEM doesn't") even though GEM models both as the single unit "Phase 1 (T1-T2)". The regex now consumes an OPTIONAL trailing ", <Region>" (alpha words only — letters/space/dot, comma-gated) after the train token, so "LNG Canada T1, BC" → site "LNG Canada", trains "T1". A PARENTHETICAL qualifier is NOT consumed (the comma gate + alpha-only class leave "Portovaya LNG T1 (+ FSU)" and "Plaquemines LNG T1-18 (Phase 1)" untouched — they still need the end-anchor right after the train token). Both LNG Canada rows now normalize to "canada" (== GEM "LNG Canada Terminal") and sum to 14, matching EXACTLY; report_diff's train-range pre-pass then aligns them to the "Phase 1 (T1-T2)" unit (see the unit-level alignment deep-dive). **Same-site country-split fix (`_merge_split_site_runs`, Atlantic/Calcasieu fix):** the centered-label problem can split a SINGLE multi-train site across a country boundary that NEITHER the per-page true-up nor `_reclaim_cross_page` can repair, because the boundary is TWO-SIDED — the donor run is simultaneously OVER its subtotal (a trailing row of the NEXT country attached to it) and SHORT a leading row (the first train inherited the PREVIOUS country). On liq page 33: "Atlantic LNG T1 (Mothballed)" sits above the centered "Trinidad &" label so T1 inherits Russia while T2/T3/T4 are Trinidad; the first "Calcasieu Pass LNG T1-6" row inherits Trinidad's label while T7-12/T13-18 are USA (so Trinidad reads 15.2 vs its 14.8 subtotal — never "short", so the reclaim never fires — while Russia's non-contiguous Sakhalin segment collapses its subtotal in `_robust_subtotal_map`). A run of consecutive rows with an IDENTICAL site_name spanning >1 country is an unambiguous signal (GIIGNL never lists one terminal under two countries — GTA Tortue, the lone cross-border case, is an `_SITE_COUNTRY_OVERRIDES` entry). The pass unifies each such group to the country that, on receiving the WHOLE group, lands CLOSEST to (and within `reach_high` of) its published subtotal — the two anchors make the closest-fit target the genuine owner (Oman's 11.4 completes to 11.5 with both Oman trains; USA's 115.4 would balloon to 119.4). Iterated to a fixpoint because groups chain through a shared donor (Calcasieu must vacate Trinidad before Trinidad can receive Atlantic). Runs BEFORE `_reassign_country_islands`/`_reclaim_cross_page`. Verified report-wide to fire ONLY on the four real bugs (Atlantic, Calcasieu, Oman T1, Brunei T1/T2). **`_SITE_COUNTRY_OVERRIDES` gained a REGAS entry ("oristano"→Italy):** GIIGNL's "Oristano, Sardinia" (HIGAS micro-terminal, 0.2 MTPA) is Italy's LEADING regas row but sits just above the centered "Italy" label, so it inherits Greece; the per-page true-up can't reclaim it because Italy's other rows already land within ~1% of its 22.3 subtotal (22.1) — Italy never reads "short" so the 0.2 row is stranded. Oristano/Sardinia is unambiguously Italy, so a site override is the auditable fix. **Owner-cell cross-row attribution (`_attribute_owner_fragments`, owner-bleed fix):** the OWNER column is the one cell that routinely spans MULTIPLE physical lines, and GIIGNL vertically *centers* it on the row's data line, so it STRADDLES the data line (a 2-line owner sits on the lines above AND below, leaving the data line's own owner slice blank) and a long owner OVERFLOWS toward the next row. The generic `_partition_lines_by_data` (tuned for the name column) assigned these owner-only lines to the nearest data line / the row above on a tie, bleeding one terminal's owners into its neighbour: Mejillones got just "(37%)" while "ENGIE (63%), Ameris Capital" bled up to Saint John; Acajutla's "Energia del Pacifico" head bled to Andrés and its "Centroamerica)" tail to Montego Bay; Escobar's "(50% Enarsa, 50% YPF)" tail bled down to Bahia; the dense Japan regas block fused adjacent terminals. So the owner column gets a DEDICATED pass (run after the partition in both page extractors; the result overrides only `merged["Owner(s)"]`/`["Owner"]`, leaving name/number/vessel on the generic partition). It attributes each owner line LOCALLY (no cross-row propagation → no drift) by its two bracketing data lines: strictly-nearer wins; a distance TIE is broken by FAR-SIDE centring symmetry (the line belongs to the neighbour that has a matching owner line at the same distance on its OTHER side — so Escobar's dist-2 tail stays with Escobar because "Owner: Excelerate" sits dist-2 above its data line, while Mejillones's dist-1 straddle goes down to the blank-owner Mejillones data line which has "(37%)" dist-1 below), defaulting to the lower row; and a CONTINUATION fragment — a dangling close-paren ("Centroamerica)", "and Mitsui)") or a bare wrapped stake ("(20%)") — snaps to the nearest data line at/above it. A data line's own non-blank owner is the cell centre → its own row. This cut cross-row owner bleed ~by half and let Mejillones/Caofeidian/etc. match GEM (Caofeidian now owner-corroborates to Tangshan-PetroChina and leaves `report_only` entirely); RESIDUAL bleed remains in the very densest blocks where two adjacent multi-line owners of similar extent genuinely interleave (some Japan/Mexico/China rows — a lone stray "(NN%)" or a lost head/tail), surfaced as a lone-token owner delta (NEEDS RESEARCH or a benign verdict noting "extraction artifact"). **Edition archive:** every GIIGNL edition 2020–2026 is committed in `data/` — all genuine PDFs (v1.4–v1.7) with usable `pdftotext` text layers, so this same pipeline applies to all of them (the page numbers and column offsets here are 2026-tuned; older editions need per-edition re-derivation — see `data/README.md`, and the Reconciliation SOP Appendix A.8). The legacy zip-of-JPEGs + OCR vision pipeline lives in git history only as a fallback if a future *download* reverts to that form; the editions on disk do not need it.

### `report_diff.py` — alias / project matching

Project key includes `section_type` so a single GEM terminal with both liquefaction and regasification (e.g. Sabine Pass: 6 export trains + 1 import terminal) splits into two distinct projects, not one summed entry. Alias map includes GEM `OtherNames` + `LocalNames`, with CJK transliteration via jieba + pypinyin (e.g. `中石油唐山曹妃甸LNG接收站` → `zhong shiyou tangshan caofeidian lng jieshouzhan` so distinctive city tokens can match). **Diacritic folding (Latin matching forms):** GIIGNL spells names without accents ("Pecem", "Mosjøen", "Peñuelas", "Snøhvit", country "Türkiye") while GEM keeps them ("Pecém FSRU", etc.). `normalize.py`'s `_strip_diacritics` (NFKD + drop combining marks, plus an explicit fallback map for non-decomposing letters: ø→o, đ→d, ł→l, ı→i, ß→ss, …) is applied inside the Latin-script normalizers — `normalize_terminal_name`, `normalize_country`, `normalize_entity`/`_normalize_input`, and the Latin candidate of `transliterate_to_english` — so accent-variant GIIGNL/GEM names fold to one matching token (Pecem↔Pecém, Mosjøen↔Mosjoen, Peñuelas↔Penuelas). Display values keep their accents (only the match/token/alias forms fold); the CJK path is untouched (folding leaves CJK codepoints alone, and pinyin output is already ASCII). **Row-folding (report side):** rows ending in "Expansion"/"Extension" fold into the base "<Site>" row, AND per-complex unit-code rows ("Arzew GL1Z/2Z/3Z") fold into "Arzew" (`_strip_unit_code_suffix`: trailing letters+digits token), AND explicit per-train rows ("Bontang Train E/F/G/H") fold into "Bontang" (`_strip_train_word_suffix`: trailing literal word "Train"/"Trains" + a 1-2 char code/roman numeral) — all conservative, firing only when the base resolves (a GEM key/alias, another report row, or ≥2 report peers sharing the base), so bare "expansion" artifacts are left alone. The unit-code fold deliberately ignores single-letter codes (else it eats "Senboku II"); the train-word fold needs the literal word "Train", which is what makes "Bontang Train E"→"Bontang" safe while "Corpus Christi Stage III" / "Senboku II" are left alone. **Same-name-by-owner families:** GEM disambiguates multiple distinct terminals that share a base name with a trailing first-owner parenthetical — "Tianjin LNG Terminal (PipeChina)" / "(Sinopec)" / "(Beijing Gas Group)" (common for Chinese terminals; also Salina Cruz, QatarEnergy LNG (N)/(S)). When ≥2 GEM terminals in a country+section share a base name, the parenthetical is treated as an OWNER tag, not a name token: it's added to `owners_set` and the fuzzy match-tokens are built from the base name only (so the owner word "sinopec" doesn't drag in Liuheng/Longkou (Sinopec)). Fuzzy matching strips the report-side parenthetical too, and a tie-break prefers the candidate whose GEM parenthetical owner equals the GIIGNL row's first owner. **Trailing ", <Region>" strip (matching only, `normalize.py:_strip_trailing_region`):** GIIGNL appends a province/state/emirate to many regas sites GEM never carries — "Chaozhou, Guangdong", "Saint John, New Brunswick", "Ruwais, Abu Dhabi", "Dalian, Liaoning" — so the comma defeated the otherwise-clean substring/alias/token match against GEM ("Chaozhou LNG Terminal", "Dalian LNG Terminal"). `normalize_terminal_name` now drops a single trailing `, <alpha words>` segment (letters/space/dot/apostrophe only — no digits, no second comma; comma-gated; NOT consuming a trailing "Expansion"/"Extension", left for the report-side fold; and NOT firing when the comma sits inside an unbalanced parenthetical, so "Tortue FLNG (Gimi FLNG, Greater Tortue Ahmeyim Phase 1)" and "Caofeidian (Tangshan), Hebei"→"caofeidian (tangshan)" are safe). Matching-only: display names keep the region (mirrors diacritic folding); GEM TerminalNames carry no commas so it's a no-op GEM-side. This is the general form of the LNG Canada ", BC" fix (which only stripped a region AFTER a train token); it reconciled ~25 GIIGNL China/Indonesia/Canada/UAE/Mexico/Philippines rows that were false report_only/gem_only/ambiguous splits. **Word-boundary substring (`_word_boundary_substring`):** the fuzzy substring test is now whole-TOKEN containment, not raw character substring — required once the region strip leaves bare short names: "nansha" (was "Nansha, Guangzhou") matches "guangzhou nansha" but must NOT char-substring the unrelated "longkou nanshan". Hyphen/slash count as token boundaries so "arzew"↔"arzew-bethioua" still matches. **FSRU vessel-name fuzzy match (`_fsru_vessel_match`):** GIIGNL identifies a floating terminal by its deployed vessel, which GEM also tracks in `FloatingVesselName`; an exact/containment vessel-token match between a GIIGNL FSRU row and a GEM FSRU terminal is a near-unique corroborator that GENERATES a fuzzy candidate ON ITS OWN — even when site names diverge and owners/capacity disagree. This binds Sepetiba LNG ("LNGt Powership Asia") → GEM "Sepetiba Bay FSRU" (same vessel; the 0.5-vs-2.7 capacity gap then surfaces as a real value-disagreement instead of a report_only+gem_only split), and likewise Port of Açu ("BW Magna"), Tenaga Empat ("Tenaga Satu"), Deutsche Ostsee/Mukran ("Neptune"). Gated to FSRU GEM terminals carrying a vessel name, so it never manufactures a floating-vs-onshore match. When several candidates tie, a vessel match wins outright. **Same-name family disambiguation (expanded):** after the exact-first-owner rule, two more tie-breaks fire in order: (2) the GEM paren-owner token appears ANYWHERE in the GIIGNL owner cell tokens — GIIGNL's owner text is noisy ("Sinopec 50%, Huaying 50% PipeChina (75%), Dalian" parses Sinopec first and fuses "Huaying" into one entity), so exact first-owner equality misses but the operator token "huaying" still uniquely picks GEM's "(Huaying)" over "(Huafeng)"; (3) operating-capacity preference — a GIIGNL operating row prefers the lone sibling with non-zero OPERATING capacity (Rudong: three siblings are construction/proposed at 0 operating MTPA, only "(PetroChina)" operates at 10.0 = GIIGNL's 10.0; also resolves Calcasieu Pass operating vs the 0-operating CP2 expansion). All three fire only when they isolate exactly one candidate, else the row stays `ambiguous` (the safe bucket — never a silent drop to report_only). **FSRU-vs-onshore same-port split (`_FLOAT_VARIANT_SUFFIX`, `collision_regas`):** at a regas port GEM may track BOTH a floating terminal and an onshore one under names that normalize identically — `normalize_terminal_name` strips both " FSRU" and " LNG Terminal", so "Ravenna FSRU" + "Ravenna LNG Terminal" both → "ravenna" (≈12 ports: Ravenna, Stade, Hazira, Payra, Summit Matarbari, Dongying, Yantai, Paldiski, Brunsbüttel, Wilhelmshaven TES, Haldia, FGEN Batangas). A pre-scan flags such ports (a regas (country,name) with BOTH a floating and a non-floating GEM terminal); the FLOATING member is keyed under a " fsru" name suffix on the GEM side, and a vessel-bearing GIIGNL row at that port (`_report_row_is_floating`) gets the same suffix — so onshore↔onshore and FSRU↔FSRU match instead of collapsing into one merged project (this had wrongly combined GIIGNL's onshore Ravenna 0.7 + Ravenna FSRU 3.7 into a single 4.4-vs-0.7 entry). Restricted to regasification (a report row's floating-ness is undeterminable for GIIGNL liquefaction, so liq FLNG/onshore pairs — Cameroon, Rovuma — are left merged). The suffix is non-parenthetical so it doesn't trip the family logic above. **Roman↔Arabic numeral fold (`normalize._canon_numerals`):** GIIGNL spells a numbered terminal in Arabic ("Sakhalin-2") while GEM uses Roman ("Sakhalin II LNG Terminal"); `normalize_terminal_name` canonicalizes a WHOLE-TOKEN roman numeral to Arabic (ii→2, iii→3, …) and splits a hyphen that joins a stem to a numeral ("sakhalin-2"→"sakhalin 2"), so the two forms exact-match. It only canonicalizes the SPELLING of a number — never merges different numbers — so "Map Ta Phut 1"/"2", "Senboku 1"/"2" stay distinct (GIIGNL's "Senboku I"/"II" then map 1:1 to GEM's "Senboku 1"/"2"); the GEM-universe scan found only Coatzacoalcos II / Eni Congo FLNG II / Sakhalin II carrying a standalone roman numeral, none colliding once folded. **Apostrophe fold (`normalize_terminal_name`):** straight/curly apostrophes are removed (joined, not space-split) so a pinyin-romanization name matches its apostrophe-free GEM transliteration alias — GIIGNL "Hua'an"→"huaan" matches GEM (Shenzhen Gas)'s alias "shenzhen huaan lng project"; "Nan'ao"→"nanao". **Country-map additions (`normalize._COUNTRY_MAP`):** GIIGNL abbreviates a few country names GEM keeps in long form — "Congo"→"republic of the congo" (Eni's Tango/Nguya FLNG are at Pointe-Noire, RoC; kept distinct from the DRC), "Dominican"→"dominican republic" — pure country-key mismatches that had blocked otherwise-clean matches (Congo FLNG, Andrés). Also added owner-map entries that unblocked owner-corroborated fuzzy matches: FortisBC (Tilbury), Kansai Electric (disambiguates GIIGNL "Himeji LNG"→GEM "Himeji Joint", owner Kansai, over "Himeji LNG Terminal", owner Osaka Gas). **Numbered-sibling tie-break (`_trailing_numeral`):** when the GIIGNL name ends in a numeral and the candidates are numbered siblings, restrict to the candidate whose canonical name carries the SAME trailing numeral (Map Ta Phut "Terminal 1"→GEM "…1", "2"→"…2"). The number is the only distinguishing token but is too short for `_tokens_4plus`, so substring (via a short OtherName like "Map Ta Phut") and the ≥2-shared-token rule otherwise fire for every sibling and the row falls to `ambiguous`. Fires only when exactly one candidate matches the numeral. **All-cancelled candidate exclusion:** a GIIGNL liq/regas row is operating-only, so a GEM project whose every unit is CANCELLED (status_set ⊆ {cancelled}) is dropped from the fuzzy candidate pool — without it, operating "Caofeidian (Tangshan)" (PetroChina, 10.0) substring-matched the cancelled "Caofeidian FSRU" (0 op) as a confident-but-wrong fuzzy because the correct operating Tangshan/PetroChina candidate lost its corroboration to a bled owner cell; dropping the cancelled shell lets it fall to report_only (a coverage note) instead. Scoped to ⊆{cancelled} so a terminal with any non-cancelled phase (Saint John's operating import facility) is untouched. **Stage/Phase fold (`_strip_stage_suffix`):** GIIGNL splits a later phase that GEM keeps as UNITS of the existing terminal ("Corpus Christi" + "Corpus Christi Stage III" → one GEM "Corpus Christi LNG Terminal"); the literal word "Stage"/"Phase" + a numeral folds it into the base (when the base resolves to a GEM key/alias or another report row), surfacing the Phase-3 operating-status finding (GIIGNL counts the trains operating, GEM has them construction) as a capacity conflict on the matched terminal (21.0 vs 15.0) rather than a misleading report_only. "Senboku II" has no Stage/Phase word, so it is never folded by this. **Vessel-relocation exception in the vessel-match preference:** a vessel that RELOCATED leaves its name on GEM's OLD (now non-operating) terminal — GIIGNL "Deutsche Ostsee/Mukran" carries vessel "Neptune", which GEM keeps on the proposed/retired "Lubmin FSRU" (0 op) even though the operation moved to the operating "Mukran FSRU" (9.92, "Energos Power", OtherNames "Mukran/Deutsche Ostsee"). The vessel-match preference is now SUPPRESSED when the lone vessel-hit candidate has zero operating capacity but another candidate operates and the GIIGNL row is operating — letting the operating-capacity tie-break pick the live site (corrected a prior-sweep mis-match Lubmin→Mukran) **Agent match-override escape hatch (`_load_match_overrides`/`_apply_match_overrides`, Putian/Fujian fix):** the operating-capacity & owner tie-breaks above fire only on the FUZZY same-name-family path — an EXACT canonical name hit is taken at face value, with nothing to question it. So when GIIGNL's name exact-matches one GEM terminal verbatim but actually denotes a DIFFERENT same-token terminal at the same port, the matcher silently takes the wrong one: GIIGNL "Putian, Fujian" (6.3 MTPA operating, owner CNOOC 60% / Fujian Inv & Dev 40%) normalizes to "putian" and exact-matches GEM "Putian LNG Terminal" — but that is the HANAS construction site (0 operating, Hanas/Ningxia Masite owner), while the real operating terminal is GEM "Fujian LNG Terminal" (CNOOC, 6.3, same owner split). Canonical-wins (an alias can't overwrite a canonical key) means an OtherNames alias on the correct terminal CAN'T fix it — the Hanas terminal always claims "putian". The fix is an agent-authored `staged_match_overrides.json` (auto-discovered beside the extracted CSV, or `--match-overrides`): each entry pins a report row `(country, report_site_name, section)` to a GEM `terminal_id`, resolved to its project key and applied as a `_forced_gem_key` (the same mechanism the multi-terminal FSRU split uses) right after the prose pass / before the matching loop reads `forced_gem`. The pinned match shows `match_type="override"` with a `match_override` basis string; the displaced same-token terminal falls to gem_only and, being non-operating, drops out of gem_only_operating (correct — GIIGNL's operating tables never list it). Nothing is auto-applied to GEM (§3.8); the override only corrects which GEM terminal the GIIGNL row is compared against. This is the deterministic-matcher escape hatch for the name-shape-match-miss class (city↔terminal aliases, same-port same-token siblings) — use it only when capacity/owner unambiguously identify the true terminal, and prefer it over a build-side patch so the diff JSON itself is correct (verdicts/FSRU checks read the diff).

### `report_diff.py` — unit-level alignment

`_align_units`: within a matched project, aligns each GIIGNL row to a specific GEM unit when the GEM unit name is a token of the GIIGNL site name (GIIGNL "Arzew GL1Z" ⊃ GEM unit "GL1Z") + capacity corroboration → `match_granularity="unit"` with a `unit_matches` list; falls back to project-total (operating-only) when GIIGNL rows don't map to GEM unit names (Taichung). **Train-range pre-pass (`_train_numbers`, LNG Canada T1-T2 fix):** GEM frequently models a SPAN of trains as ONE unit whose name encodes the range it covers — "LNG Canada Terminal" → unit "Phase 1 (T1-T2)" (14.0); "Brunei LNG" → "T1-T5"; "Plaquemines" → "Phase 1 (T1–24)" — while GIIGNL splits the same span across per-train rows ("LNG Canada T1" 7.0 + "LNG Canada T2" 7.0). The plain token-subset alignment below can't bridge this (GEM unit tokens {phase,1,t1,t2} ⊄ report site {canada}), so BEFORE that pass `_align_units` runs a range pre-pass: each OPERATING GEM unit naming ≥2 trains (`_train_numbers` expands "T<a>-T<b>"/"T<n>" tokens to a set of train numbers; widest range claimed first) absorbs the as-yet-unclaimed report rows whose train numbers ⊆ its range, SUMMING their capacities before the unit comparison — so GIIGNL T1+T2 (7+7=14) ↔ GEM "Phase 1 (T1-T2)" (14) agrees as ONE unit row, instead of T1 matching the project at half-capacity (the old bogus 7-vs-14 50% conflict) and T2 orphaning into `report_only` as a false "GIIGNL has, GEM doesn't". Report-row train numbers are read from the `trains` column first, falling back to the site_name (covers rows whose suffix never stripped, e.g. "Plaquemines LNG T1-18 (Phase 1)"). Restricted to OPERATING units (GIIGNL tables are operating-only) and to ≥2-train ranges, so single-train units and non-range names ("GL1Z", "Senboku II") fall through untouched to the token pass; consumed rows/units are removed from it. Pairs with the giignl_extract region-tolerant train-suffix fix (a trailing ", BC" no longer blocks the "T1"/"T2" strip), which folds the two GIIGNL rows into one "LNG Canada" project so they match EXACTLY (14-vs-14, `match_type="exact"`) rather than fuzzy. Blast radius is the ≥2-train range units only (Brunei/Plaquemines now show the same capacity finding as a unit row instead of project-total; Qatar/Calcasieu/Malaysia unchanged). **Sub-terminal designator → GEM unit (Pass 1.5, `_unit_designators`):** GIIGNL splits a complex into sub-terminals, each its own report project ("QatarEnergy LNG S(1)/S(2)/S(3)"), while GEM splits the SAME complex into one terminal with train-range units ("QatarEnergy LNG (S)" → units "S(1) T1-2"/"S(2) T3-5"/"S(3) T6-7") — a many-report-projects-to-one-GEM-terminal shape `_align_units` can't reach (GEM unit tokens {s(2,t3,5} ⊄ report site {qatarenergy,lng,s(2}), and the plain project matcher would wrongly compare each sub-terminal against the WHOLE terminal (the bogus S(2)=14.1 vs (S)=36.3 "61% conflict"). A report project carrying a parenthesized-digit designator (S(2)→"s2") that identifies exactly ONE GEM unit within a SINGLE GEM terminal in the same country+section is matched to that UNIT (`match_type="unit_designator"`, compared at unit level: S(2) 14.1 vs unit 14.1), gated on a 4+ name-token or owner overlap. The designator inherently routes n*→(N), s*→(S), so it ALSO disambiguates GEM's same-base-name siblings without the parenthetical-owner heuristic. **GEM owner parsing** now uses `parse_entity_list` (same as the report side) instead of a comma-only split: GEM cells are ";"-separated with "[NN%]" brackets ("QatarEnergy [70%]; Exxon Mobil Corp [30%]"), and the old split collapsed every multi-owner cell to a single (often wrong) tag, manufacturing false owner conflicts on nearly every match (`parse_entity_list`'s %-regex now also accepts "[…]" brackets; "qatar energy" added to the entity map). **Owner ∪ parent alignment (`_owner_alignment`):** GEM records the lower-level (JV / operating-company) owners in `owner` and the ULTIMATE PARENT companies in a separate `parent` field; GIIGNL may name an entity at EITHER level — Escobar: GEM owner "UTE Escobar", parent "ENARSA; YPF"; GIIGNL lists Enarsa + YPF; Ichthys: GEM owner "Ichthys LNG Pty Ltd", parent the 11 shareholders GIIGNL lists. So the owner-DELTA computation (at all match levels — project exact, `_unit_designators`, fuzzy) compares the report owners against GEM `owner` ∪ `parent`: `owners_report_only` = report owners in NEITHER (a real delta), `owners_gem_only` = GEM OWNERS absent from the report (parents are supplementary, not expected in GIIGNL, so not gem-only), and a new `owners_matched_via_gem_parent` records which GIIGNL entities aligned only at the parent level (transparency). This removed ~70 false owner deltas in the 2026 batch. IMPORTANT — only the DELTA reporting uses owner ∪ parent; the match GATING / candidate generation stays owner-LEVEL (a shared ultimate parent — a national oil company — is too broad to IDENTIFY a terminal and would spawn spurious candidates / ambiguity; verified that folding parents into the gate turned a clean Caofeidian-type match ambiguous, hence the split). **Project-spanning guard:** a unit is accepted only if the GIIGNL row's capacity is at least as close to that unit as to the project total — stops a whole-terminal GIIGNL row from being pinned to one unit via a coincidental code token (GIIGNL "Portovaya LNG T1 (+ FSU)" = 1.5 = the whole terminal would otherwise emit a spurious unit-level 100% conflict against GEM unit "T1" = 0.75 beside the correct project-level 1.5-vs-1.5 match). **Multi-terminal FSRU site split (`_split_multiterminal_fsru_sites`):** GIIGNL labels several physically distinct FSRU terminals at one port with the SAME site name, disambiguating only by vessel — e.g. Germany "Wilhelmshaven" appears twice (Höegh Esperanza, Excelerate Excelsior), which GEM tracks as two terminals ("Wilhelmshaven FSRU" + "Wilhelmshaven TES FSRU"); Egypt "Ain-Sokhna" lists three vessels split across GEM "Ain Sokhna FSRU" (Energos Power) and "Sumed FSRU" (Höegh Galleon, Energos Eskimo). Each GIIGNL vessel row is routed to the GEM terminal whose **terminal-level `FloatingVesselName`** carries it (GIIGNL "Excelerate Excelsior" ⊇ GEM "Excelsior"), and the site is emitted as one report sub-project per GEM terminal (display name carries the vessel, e.g. "Wilhelmshaven (Höegh Esperanza)"), each force-matched. Fires only when the site's vessels resolve to **≥2 distinct GEM terminals** AND every row maps — distinguishing it from the sequential-berth case below. **FSRU operating-only (`_fsru_operating_report_capacity`):** for a genuine single-terminal berth that cycled vessels (one GEM operating unit + retired vessels) where GIIGNL lists every deployed FSRU as an operating row, the report capacity is recomputed as the sum of only the GIIGNL rows whose vessel (matched against GEM `unit_name`) maps to a GEM OPERATING unit; the others become per-vessel notes in `disagreements`. Also emits `nonoperating_units` (non-op units of matched projects) for the `audit_nonoperating` sheet. **Missing ≠ zero capacity (`capacity_known`):** each GEM unit carries a `capacity_known` flag (False when the GEM capacity cell is blank/unparseable); `capacity_mtpa` stays a float (0.0 sentinel) so all the capacity arithmetic above is unaffected, but the non-operating sheet emits `None` (→ blank cell) for an unknown-capacity unit instead of a misleading `0` — a cancelled/proposed unit GEM never sized (Pluto LNG Terminal T3, Nigeria T08-T12, …) is unknown, not zero. There are normally zero genuine-0.0-capacity non-op units, so any `0` showing on that sheet is the bug this guards against. **Non-operating GIIGNL rows (Bontang/Balhaf fix):** a report row carrying a `status` (set by giignl_extract from a "(Mothballed)"/"(stopped)" hint, i.e. status ∈ `_NONOP_STATUSES`) is split out of the report project into `nonop_rows` and EXCLUDED from `total_capacity_mtpa`/`trains_count`/`rows` — so the operating comparison sums only the operating trains (Bontang report=F+G+H=8.7 vs GEM operating G+H=5.75, NOT 11.6; Balhaf both-trains-stopped → report 0 vs GEM 0, killing the old spurious 7.2-vs-0). The excluded rows surface on the match as `report_nonoperating` (operating sheet column, no red), and `_corroborate_nonop` aligns each to the GEM non-op unit whose name is a token of the row's site_name+trains (lowercased — `_simple_tokens` doesn't case-fold and `trains` isn't normalized), filling that unit's `giignl_narrative_mention` + clearing its `is_gem_only` flag (Bontang E↔unit E idled; Balhaf T1/T2↔GEM T1/T2 mothballed). Tiny blast radius — only fires when a GIIGNL row actually carries a status (≈4 rows in the 2026 edition). **§3.2.1 prose operating-status corrections (Bontang Train F fix):** GIIGNL's TABLE is operating-only but its NARRATIVE can say a train listed *untagged* in the table isn't actually operating — Bontang p.31: "only Trains G and H currently in operation" means Train F (untagged in the table, no "(Mothballed)") is idled too. The narrative pass is agent-driven (SOP §3.2.1), so this is fed via an agent-authored `giignl_prose_corrections.json` (auto-discovered next to the extracted CSV, or `--prose-corrections`): `_load_prose_corrections` + `_apply_prose_corrections` run right after the FSRU split and BEFORE matching, moving each named unit's report row from `rows`→`nonop_rows` (status from the file, default idled), recomputing the operating total, and stamping `_prose_source` (the citation flows into `report_nonoperating` and the corroboration note). This drops Bontang from a bogus report 8.7-vs-5.75 (51%) to 5.8-vs-5.75 (0.9%, just the per-train cap nuance, G+H both 2.9 in GIIGNL vs 2.8/2.95 in GEM) — F now corroborates GEM's idled F via prose. Capacity NUMBERS are never changed here (§5.6 prefers the tabular value); nothing is applied to GEM (§3.8) — it only makes the GIIGNL side internally consistent with GIIGNL's own prose. The file's second section, `nonop_corroborations`, handles the related case where a GEM non-op unit has NO GIIGNL table row because the unit already ceased (NWS Train 2: dropped from the operating table, but the narrative names it "permanently ceased") — `_load_prose_corrections` returns `{op, nonop}`, and the nonoperating-units pass fills `giignl_narrative_mention` + clears `is_gem_only` for the named GEM unit (keyed GEM terminal+unit). **GEM unit researcher notes + non-op capacity explanation (`_gem_nonop_capacity_explanation`, Corpus Christi / issue #6):** each GEM unit dict now carries its `researcher_notes` (colmap key `researcher_notes_unit`, read by key never index), which (a) flows onto each `nonoperating_units` record (surfaced in the new `researcher_notes` column of `audit_nonoperating`) and (b) feeds a `gem_nonop_explanation` attached to every operating match in the same post-pass that attaches `gem_capacity_source`. The explanation summarizes the project's forward (construction/proposed) non-op units — name, status, capacity — plus every non-op unit's note (`_PREOP_STATUSES` = construction/proposed; retired/mothballed excluded since their capacity wouldn't inflate a current GIIGNL operating total). This is the data the build's verdict layer uses to recognize the "GIIGNL counts trains as operating that GEM deliberately holds as construction" shape (Corpus Christi: GIIGNL 21/7-trains operating vs GEM 15 operating + Stage 3 T04-T10 held construction, with RR's "commercial operations not declared" note) and to STOP the GIIGNL-edition-supersede rule from blind-bumping GEM's operating capacity — see the `build_review_package.py` deep-dive. Pure data propagation here; the decision lives in `_classify_disagreement`

### `report_diff.py` — `parse_report_owner` (GIIGNL owner-column parser)

Splits the GIIGNL Owner cell into roles — `Owner:`/`FSRU:` = VESSEL owner (→ GEM `vessel_owner`, kept OUT of the terminal owner-set so it doesn't manufacture false deltas on every FSRU); `Charterer:`/`Sub-charterer:`/`Terminal:`/`GNLQ:`/bare = TERMINAL owner. Paren-aware (a shareholder list `(50% Enarsa, 50% YPF)` stays one segment, not the old "50% YPF)" garbage); strips a leading or trailing `%`; expands a named parenthetical into the holding co + its shareholders. The diff owner-set = terminal owners + shareholders.

### `build_review_package.py` — operating-diff verdict classifier

`_classify_disagreement(m, suppress_nonop_insight=False)` turns each flagged `audit_operating` row into the human-facing `insight` + `suggested_resolution` cells (the rule spec is mirrored in the `audit_operating` `SHEET_DESCRIPTIONS` entry). It runs a sequence of deterministic rules and, for anything it can't settle (a material non-GIIGNL capacity conflict or a non-benign owner delta), emits a `NEEDS RESEARCH` placeholder (light-yellow fill) that the agent research pass overrides via `staged_recon_verdicts.json` (`_recon_verdicts_lookup`, keyed `(terminal_id, section_type, unit_name|'')`). Capacity-facet rules, in order: (1) **status-lag** — `gem_operating_units==0` → "GEM status likely current, verify restart" (returns early, so an all-non-op terminal never reaches the rules below); (2) **non-op-explains-shortfall** (`_nonop_explains_shortfall`, issue #6) — GIIGNL operating capacity EXCEEDS GEM's by a material margin AND the project has construction/proposed GEM units whose combined capacity covers the gap (within `_SHORTFALL_COVER_TOL_MTPA`, the rounding/estimate slack): GIIGNL is counting trains as operating that GEM deliberately holds non-operating, so this **PRE-EMPTS** rule (3) and emits "do NOT bump GEM capacity; verify status only", quoting the GEM researcher note (`_quote_researcher_notes`) from the diff's `gem_nonop_explanation` and echoing it into `analyst_note`; (3) **GIIGNL-edition-supersede** — GEM capacity's SOLE source is an older GIIGNL edition (`gem_capacity_source`) → "replace with GIIGNL 2026"; (4) **same/newer-edition-yet-differs** and (5) **<5% rounding** and the **FSRU nameplate-vs-sendout** metric branch. Owner facet: `_owner_delta_is_benign` (same-entity name-variants/aliases, shareholder-vs-vehicle granularity) → "no action", else NEEDS RESEARCH. **Why (2) is conservative:** it fires only on `report>gem` by more than the tolerance with forward-phase units actually covering the gap — so it can't swallow a genuine stale-edition bump where GIIGNL merely re-measured the same operating trains. **`suppress_nonop_insight`:** the sheet builder sets this true when a `staged_recon_verdicts.json` entry (without its own `insight`) will supply the resolution; rule (2) then still settles the capacity facet (no dangling NEEDS RESEARCH) but emits a neutral "see suggested_resolution for the researched determination" instead of asserting the structural narrative — because a human may have found a different cause (Yuedong: the gap was a genuinely stale OPERATING capacity, not the construction Phase 2 the heuristic points at; the staged verdict says "replace 3.0 with 5.0", and the deterministic insight must not contradict it). In the 2026 batch rule (2) fires on 13 matches; 5 of those route to status-lag (op=0) first, and of the 8 it actually classifies, 7 have a staged verdict (so the sheet shows the researched text + neutral insight) and only Corpus Christi takes the full deterministic do-not-bump path.

**Read / revisit the source when:** a capacity recommendation is wrong (trace which of rules 1–5 fired — `_nonop_explains_shortfall` vs the edition rule is the usual confusion); the non-op-shortfall rule over- or under-fires (tune `_SHORTFALL_COVER_TOL_MTPA` or the `report>gem` margin; confirm the project's `gem_nonop_explanation.preop_units` is populated upstream in `report_diff.py`); a researched staged verdict and the deterministic insight tell contradictory stories (check the `suppress_nonop_insight` plumbing); an owner delta is wrongly flagged/benign (`_owner_delta_is_benign`, `_OWNER_ALIAS_PAIRS`, `_VEHICLE_MARKERS`); a NEEDS RESEARCH placeholder isn't being overridden by a staged verdict (key must be project-level `unit_name=''` — see [[recon_verdict_insight_columns]]).
