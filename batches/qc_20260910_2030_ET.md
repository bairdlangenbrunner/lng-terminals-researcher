### 1.2 The one new finding: 66 orphan `Cost [ref]` cells that are a pull-engine rendering choice, not data loss

The completeness sweep grew from 1,207 to 1,279 gaps. All 72 additions are export-side:

- **66 `Cost [ref]` orphan refs** (citation present, `Cost` blank — Rule F shape) on 66 unit rows
  of **26 terminals**, every one a **multi-unit terminal** (2–5 units). Status mix: 26 proposed,
  16 operating, 14 construction, 7 shelved, 3 cancelled. None existed on Aug 26.
- 6 `VesselOwner`/`VesselOperator` project-field inconsistencies on Argentina LNG (same root: the
  fresh pull renders these per-unit where the old one duplicated the project value).

Traced to source. In Postgres `lng_unit.cost` is null on all 66 rows while `lng_project.cost`
**and** `lng_project.costDatasource` are populated on all 26 plants — the cost was only ever
recorded at project level. Nothing was edited: `plant_history` and `django_admin_log` show no
cost edits on these plants since Aug 20. What changed is the pull engine. `gem-db-ops` commit
`59ecb73` (2026-09-10) rewrote `gem_all_fields.py` so that the unit row falls back to the
project-level cost **only on single-unit terminals** (pushing a whole-terminal figure onto every
unit of a multi-unit terminal would multiply it), while the **citation** follows the cost's own
level regardless — so on a multi-unit terminal every unit row prints the project-level
`Cost [ref]` next to a blank `Cost`. The code comment states this mirrors what the GEM website
itself renders on those rows. So the export is now *faithful*: the orphan refs exist on the
public site too. They just weren't visible in the old export, which pushed the project cost onto
every unit row (the multiplied-cost problem — arguably the worse of the two renderings).

Consequences, none of which is an LNG-side data fix:

- The 66 rows are **not** a researcher Rule-F violation and should not be staged as deletions of
  the ref or fabrications of a per-unit cost. The completeness sweep needs to learn to tag this
  class (`project_level_cost_multi_unit`) rather than `orphan_ref` — a small `completeness_sweep.py`
  change, listed in §5.
- Whether the tracker *wants* project-level cost split across units, held at project level with a
  terminal-total column only, or left as-is is a convention question for Rob (§6).
- The 6 genuine unit-level orphans that pre-date this (`lng_unit.costDatasource` set, `cost`
  null; the 6 `Cost [ref]` `blank_ref` items in the sweep are the mirror image — cost set, no
  ref) are the actual researcher worklist here and are unchanged since Aug 26.

## 2. Citation link-rot summary (§3.2) — complete

### 2.1 Method and rules

`citation_qc.py` scanned every URL instance in every `[ref]` column (`TotTerminalCost [ref]`
excluded as derived) on 2026-08-26: **15,810 instances, 4,878 unique URLs**. Raw verdicts were
re-adjudicated on 2026-09-10 by `scripts/citation_rot_summary.py` (new — the 08-26 memo could not
be quoted reproducibly; see the SOP §3.2 note) with these rules:

- **rot** = `dead` (404 / 410 / 000 connection failure / other 4xx / soft-404) + `content_gone`
- **live** = 200 OK, 301/302/307/308 redirects, 202, and bot-challenge interstitials
- **blocked** = 401 / 403 / 429 and every 5xx — never counted as rot (CLAUDE.md "bot-block ≠ dead")
- **unverifiable** = image-only PDFs
- Intersected with the 09-10 export: **0 scanned citations have been repaired or removed** since
  the scan, so the Aug 26 verdicts are current.
- **Re-test folded in.** Per SOP §3.2 a sample of dead verdicts was re-tested through
  `url_verifier.py` with the browser UA on 2026-09-10 (`citation_retest_20260910.json`, 309 URLs):
  all 159 unique HTTP-000 URLs plus a random 150 of the 286 unique 404 URLs. A URL that now loads
  is live; one that now answers 401/403/429/5xx is blocked. The re-test overrode 145 instances.

| Re-test bucket | URLs | Still dead | Now live | Now blocked (403/429) | Other |
|---|---|---|---|---|---|
| HTTP 000 (connection failure), all of them | 159 | 101 still 000, 3 → 404 | 22 | 32 | 1 timeout |
| HTTP 404, random sample | 149 | 141 still 404 | 1 | 1 | 6 → 000 |

**Read this as: 404s are genuine rot (95% confirmed on re-test); a "000" verdict is only ~65%
rot — a third of connection failures are bot-blocks or transient.** Before anyone re-sources a
000-cited cell, re-test that URL. The 101 URLs still 000 after two independent attempts two weeks
apart are treated as rot below.
